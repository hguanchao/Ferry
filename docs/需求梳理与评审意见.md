## 一、产品全景（一句话 + 边界）

**定位**：渡口是面向内部研发团队的交付链路**编排层与增强层**，以"应用"为最小管理对象，串联"代码提交 → 构建 → 测试 → 扫描 → 制品 → 部署 → 准入 → 生产发布"全流程，叠加 AI 归因与受控动作执行能力。

**四条职责边界（PRD 特殊说明已明确，梳理确认无歧义）**：
1. 只做四件事：编排流程、守住门禁、记录全程、增强智能；不替代 GitLab / Jenkins / Nexus / K8s / Docker；
2. 流水线定义以渡口为唯一真相源，**不认仓库内 Jenkinsfile**（防绕过门禁与审计）；
3. 三种部署目标类型（SSH / Docker / Kubernetes）能力差异**不做虚假统一**，不支持项界面显性标注；
4. AI 边界：只承担读取与判断成本，不获写入与执行权力（仅 L1 低危可逆动作例外，L3 永久禁止）。

**目标用户**：研发工程师、测试工程师、发布经理、SRE 值班、平台管理员（五预置角色，RBAC 两层授权：功能权限 + 「应用-环境」二元组数据权限）。

**首期范围声明**：内部单租户（表带 tenant_id 固定默认值），多租户自助注册/计费/租户后台本期不做。

### 2.2 核心对象模型（数据视角）

```
应用 App（编码全局唯一、创建后不可改，下游全部外键引用）
 ├─ 流水线定义（版本化快照，运行绑定版本号）── 运行 Run（幂等键：应用+commit+流水线版本）
 │      └─ 阶段 Stage（8 固定类型）── 任务 Task（与 Jenkins Job 一一对应）
 ├─ 制品 Artifact（内容摘要唯一标识、不可变）── 环境标记 artifact_env（晋级链路）
 ├─ 环境 Env（每环境固定一种部署目标类型）── 部署记录 deploy_record（含校验快照）
 ├─ 发布单 RC（聚合多应用制品，一应用一制品；创建后制品锁定）
 │      └─ 影响面（三层推导）+ 风险评级（五因子加权，提交准入时锁定）
 └─ AI 输出（四类能力）── 动作记录 action_record（白名单目录 + 六项服务端校验）
横切：审计日志（只插不改，≥1 年）、门禁结果 gate_result（规则快照随运行落库）
```

### 2.3 四个状态机（正文"整体架构"章）

| 状态机 | 状态数 | 关键设计 | 评审发现的问题 |
| --- | --- | --- | --- |
| 流水线运行 | 7（排队/运行/阻塞/成功/失败/超时/已取消） | 阻塞=门禁不过等人工；断点重跑从失败阶段起 | ⚠️ "失败→运行中/超时→运行中"与功能 6"重跑创建**新**运行实例、原运行保留"矛盾（详见 6.3-D1） |
| 发布单 | 8+1（草稿/待审批/已批准/发布中/已回滚/已完成/已驳回/已取消 + 已关闭） | 单向流转不回跳；已回滚后必须新建发布单 | ⚠️ 名词解释枚举缺"已关闭"；"草稿/待审批"无取消路径（详见 6.3-D2/D3） |
| AI 动作 | 8（提议/授权/待确认/拒绝/执行中/成功/失败/已撤销） | L1 自动授权、L2 转人工、L3 拒绝记违规 | 完整，与功能 28 六项校验一致 |
| 门禁判定流程 | 文本流程 | 分支>应用>组织；规则快照随运行；数据缺失判"不适用" | 完整 |

## 三、关键产品机制梳理（可测试规则摘录）

这些机制是渡口的"安全底线"，梳理确认可测、建议测试用例直接引用：

| # | 机制 | 规则要点 | 出处 |
| --- | --- | --- | --- |
| M1 | 触发幂等 | 幂等键（应用+commit+流水线版本）：命中进行中→返回既有 run_id 标"已合并"；命中成功→复用制品标"复用运行"；60 秒内同 commit push 合并 | 功能 4 / 4.1 |
| M2 | 制品不可变 | 同版本号覆盖推送一律拒绝、无覆盖入口；晋级仅改环境标记不重建；生产仅接受经预发晋级且形态匹配制品 | 功能 11 |
| M3 | 部署锁 | 「应用+环境」分布式锁，TTL 30 分钟 + 60 秒心跳续约，异常退出到期自动释放并告警；抢锁失败不排队 | 功能 17 |
| M4 | 五校验前置 | 制品已晋级 / 形态匹配 / 环境空闲 / 依赖兼容 / 变更单已批准且窗口覆盖；服务端串行、前端绕过仍拦截记审计 | 功能 17 |
| M5 | 门禁豁免受控 | 单条粒度、理由≥20 字、有效期 8/24/72h 到期自动失效；红线规则禁豁免；带豁免发布单三处高亮 | 功能 8 |
| M6 | 双人原则 | 生产操作操作人≠确认人；自建自批强制追加一级审批；熔断后"继续发布"需权限+理由+审计高亮标记 | 功能 13/21/23 |
| M7 | 健康检查熔断 | 连续 N 次超阈才判不通过（防抖）；监控数据缺失视为不通过不放行；不支持项标注而非跳过 | 功能 23 |
| M8 | AI 证据强制 | 无证据结论服务端丢弃；置信度服务端按证据计算不采信模型自评；低置信不给动作入口；送模数据按调用者权限过滤 | 功能 25 |
| M9 | AI 动作白名单 | 模型仅选 action_id 填受限参数，禁止生成命令/脚本；一次一动作禁串联；L1 十分钟内一键撤销；频控（L1 10 分钟≤3 次、L2 小时≤2 次）；连续 2 次失败冻结 30 分钟；新应用默认 L0 | 功能 28 |
| M10 | 审计不可篡改 | 只插不改不删（DB 层限权）、留存≥1 年超期归档、凭据类仅记"已变更"、导出带水印且导出本身记审计 | 功能 31 |
| M11 | 观察期下限 | 观察时长 ≥ 该部署类型回滚时效承诺的 2 倍，低于报错 | 功能 15/23/24 |
| M12 | 回滚时效闭环 | 承诺值（K8s≤2min / Docker≤5min / SSH≤15min）+ 实际耗时记录，近 5 次最大值超承诺即在环境页提示重估策略 | 功能 16/24 |

**结论**：虽无资金场景，PRD 在"发布安全"上等效实现了**幂等（M1）+ 一致性防线（M2–M4、M7）+ 全程留痕（M10）**三件套，且危险操作二次确认、可撤销、双人管控覆盖完整，这部分设计质量高，评审时不建议任何排期压力砍除 M1–M4、M9、M10。

## 八、MVP 切分与版本规划建议（待产品负责人拍板）

**最小可行闭环**：应用建档 → 流水线定义/触发/运行 → 门禁 → 制品入库/晋级 → 测试·预发部署 → 发布单准入 → 生产发布（单类型）。

| 版本 | 范围 | 砍入理由 |
| --- | --- | --- |
| MVP（试点 ≤20 应用） | 应用管理 35–37；流水线 1–6 + 38；门禁 7–9；制品 10–11；环境与部署 13–18（**仅 Kubernetes + GitLab**）；发布准入 19–21；生产发布 22–24；系统管理 30–31；AI **仅失败归因规则引擎部分** | K8s 回滚时效最短风险最低（待确认问题 1 建议 SSH 最后接入）；GitLab 内网 webhook 无公网中转问题（消解 Blocker 15）；规则引擎归因不依赖模型部署决策（消解 Blocker 7） |
| V2 | GitHub/Gitee 适配器（webhook 中转结论后）；Docker 执行器；变更单 36；通知渠道 37；存储策略 38；AI 模型推理四类能力 + 动作引擎 L1（默认 L0 灰度）；开放 API 39 | 按依赖就绪度顺序接入 |
| V3 | SSH 执行器（目标机条件核实后）；AI L2 授权；技术债看板 40；效能看板完整化 | 低频/低优先 |
| 后续版本池 | 群组批量导入（若建档成本实测超标再立项）；多租户能力 | 明确"本期不做"，防范围蔓延 |
